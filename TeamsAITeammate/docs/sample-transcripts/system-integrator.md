# サンプル会議スクリプト: SIer (System Integrator)

## スクリプト 1: 大規模基幹システム移行プロジェクト キックオフ

**会議名:** A社 基幹システムモダナイゼーション Phase2 キックオフ  
**参加者:** 村上（PM）、野田（アーキテクト）、橋本（インフラリード）、吉岡（A社側情シス部長）

---

**村上:** Phase1 のアセスメント結果を踏まえて、Phase2 のマイグレーション計画を決めたいと思います。野田さん、アーキテクチャ方針の説明をお願いします。

**野田:** はい。現行の COBOL バッチ 1,200本のうち、810本は単純な変換でJavaに移行可能です。残り390本が問題で、複雑なビジネスロジックが埋め込まれています。ここで大事なのは、過去の経験から言うと「全部一気に移行する」と100%失敗します。2019年のB社案件で、1,500本を一括移行しようとして、テスト工数が想定の4倍に膨れ上がって、最終的にプロジェクトが1年延期になりました。

**吉岡:** それは避けたいですね。どういうアプローチを提案されますか？

**野田:** ストラングラーパターンで段階移行します。まず影響の小さい参照系バッチ300本を先行移行して、パイプラインとテスト手法を確立する。その上で更新系に進む。重要なのは、移行中は新旧並行稼働にして、結果の突合を毎日自動で回すことです。突合不一致があった場合、旧システム側を正とする運用ルールを最初に決めておく。前回C社案件では、このルールを決めずにスタートしたせいで、不一致が出るたびに会議が紛糾しました。

**橋本:** インフラ面で一点。現行のメインフレームの夜間バッチウィンドウが22時〜6時の8時間なんですが、実際には土日や月末のピーク時に8時間を超過してることがあります。監視ログを分析したら、月末の請求バッチが7時にずれ込んでいるケースが年に4回ありました。移行後のクラウド基盤は、このピーク時のオートスケーリングを前提に設計する必要があります。

**村上:** 吉岡さん、現行システムのバッチ仕様書って最新化されてますか？

**吉岡:** 正直に言うと、10年以上前のドキュメントがそのまま残っているだけで、実態と乖離している可能性が高いです。特に2018年の消費税改正と2020年のインボイス対応で、プログラム自体は改修されてますが、設計書は追従してません。

**野田:** であれば、最初に現行システムのリバースエンジニアリングをやる必要がありますね。ソースコード解析ツール（CAST AIP）でコールグラフとデータフローを自動抽出して、実態の仕様書を作り直す工程を入れましょう。これ、過去の経験上、全体工数の15〜20%を占めますが、ここをケチると後で3倍返しで来ます。

## スクリプト 2: クラウドネイティブ化 設計レビュー

**会議名:** D社 EC プラットフォーム リアーキテクチャ 設計レビュー  
**参加者:** 石川（アーキテクト）、松井（バックエンドリード）、永井（SRE）、川口（D社CTO）

---

**石川:** マイクロサービス分割の方針を決めたいんですが、まず松井さんから現状分析を。

**松井:** 現行のモノリスを分析した結果、ドメイン境界が8つ特定できました。商品、注文、在庫、決済、配送、顧客、プロモーション、レビューです。ただ、注文と在庫は結合度が非常に高くて、分離すると分散トランザクションが必要になります。

**石川:** そこが一番の設計判断ポイントですね。結論から言うと、注文と在庫は1つのサービスに留めるべきです。分散トランザクションは理論的にはSagaパターンで解決できますが、実装の複雑度が跳ね上がります。E社案件で在庫と注文を分離したんですが、競合状態で在庫がマイナスになるバグが本番で発生して、2ヶ月間修正に費やしました。あの時学んだのは「分割しすぎない勇気」も大事だということです。

**川口:** パフォーマンスの観点で心配があるんですが。今の商品ページの応答時間が200msで、これより遅くなると売上に影響します。

**永井:** SRE的な観点でいうと、マイクロサービス化すると必然的にネットワークホップが増えるので、レイテンシは悪化方向です。対策としてはBFF（Backend for Frontend）パターンとGraphQLで、必要なデータだけを1リクエストで取得する設計にします。あと、ここが重要なんですが、サービスメッシュのサイドカーがリクエストあたり2〜5msのオーバーヘッドを追加します。Istio を入れる場合、最初にベンチマークを取って許容範囲かどうか確認しないといけません。前回のF社案件でこれを見落として、本番投入後に応答時間が30%悪化して大問題になりました。

**松井:** あと、データ移行戦略ですが、サービスごとにDBを分離する場合、結果整合性をどうするか。特に在庫数の参照で問題になるのが「売れたのに在庫切れ表示」と「在庫あり表示なのに注文失敗」のどちらを許容するか、ビジネス判断が必要です。

**川口:** ECの文脈では「在庫あり表示なのに注文失敗」の方がユーザー体験としては最悪ですね。

**石川:** であれば、在庫は「楽観的更新」で、表示の遅延は許容するが、注文確定時に悲観的ロックを取る方式ですね。これ、Amazon のPatent公開されている設計と同じ考え方です。

## スクリプト 3: 障害対応振り返り (ポストモーテム)

**会議名:** G社 決済システム障害 ポストモーテム  
**参加者:** 梅田（部長）、原（インフラ）、北村（アプリ）、沢田（運用）

---

**梅田:** 3月15日 14:23〜16:45 の決済停止障害について振り返ります。影響は約2.5時間、推定影響金額は3,200万円の取引が滞留しました。まず原さん、時系列を。

**原:** 14:23 にデータベースのコネクションプールが枯渇してアプリケーションが応答不能になりました。根本原因は、その直前の 14:15 に実行された日次バッチの一つが、本来2分で終わるところ、テーブルロックを取得したまま応答しなくなったことです。

**北村:** バッチが固まった理由なんですが、前日にデプロイしたホットフィックスで、クエリのWHERE句のインデックスが効かなくなる変更が含まれてました。テストDBでは問題なかったんですが、本番のデータ量（5000万件）だとフルスキャンになってしまう。

**梅田:** なぜテストで検出できなかったんですか？

**北村:** テストDBのデータ量が本番の1%しかないので、クエリプランが異なるんです。これ、実は以前から認識されてた問題で、本番相当のデータ量でのパフォーマンステストをCI/CDに組み込むべきだと何度も提案してきたんですが、コスト面で見送られてました。今回の障害損失を考えれば、年間のテスト環境コスト（約500万円）は安いものです。

**沢田:** 運用の観点で反省点があります。コネクションプールの枯渇アラートは 14:23 に発報されたんですが、最初の対応（バッチ強制停止）を実行したのが 14:52、つまり29分かかってます。原因は2つ。1つは、当日の当番がこの種の障害を初めて経験する若手だったこと。もう1つは、ランブックに「コネクションプール枯渇時の対応手順」が書かれてなかったこと。DBをkillする権限を持ってる人が限られてて、エスカレーションに時間がかかりました。

**原:** そうなんです。本来はDBのkillコマンドは秒殺で実行すべきなんですが、過去に「間違って本番のバッチを殺してしまった」事故があって以来、DB操作は2名確認必須というルールになってます。でも障害時はスピード優先にすべきで、このルールに例外条件を設けるべきです。

**梅田:** 再発防止策をまとめましょう。1）テスト環境のデータ量増強、2）ランブックの整備、3）障害時のDB操作権限の緩和ルール策定。あと一つ。根本的な対策として、バッチ処理のタイムアウトを設定すべきです。5分以上かかるバッチは自動で中断するサーキットブレーカーを入れましょう。

**沢田:** タイムアウト値なんですが、今まで運用で見てきた経験上、正常なバッチでも月末処理は通常の3倍の時間がかかることがあるので、固定のタイムアウトではなく、過去の実行時間の平均+3σで動的に設定する方がいいです。

## スクリプト 4: AI/ML 基盤構築提案 プレゼン準備

**会議名:** H社向け MLOps 基盤構築 提案内容レビュー  
**参加者:** 西村（営業）、小川（データサイエンティスト）、加藤（クラウドアーキテクト）、斎藤（PM候補）

---

**西村:** H社向けの MLOps 基盤構築の提案書レビューです。先方の要件は、現在 Jupyter Notebook で属人的に回しているMLモデルを、CI/CDパイプラインに載せて運用自動化したいということです。

**小川:** 技術選定で重要な点ですが、H社のデータサイエンティストは全員 Python ユーザーで Kubernetes の経験がありません。なので、Kubeflow のような K8s ネイティブのツールを入れると、学習コストで頓挫します。実際、I社案件で Kubeflow を導入したんですが、半年経っても DS チームが使いこなせず、結局「Kubeflow の前に立つ人」が必要になって、属人化の問題が解決しませんでした。

**加藤:** であれば Azure Machine Learning か SageMaker のマネージドサービスの方がフィットしますね。ただ、H社は既にAzure環境を持っているので Azure ML 推しですが、一つ落とし穴があって。Azure ML のパイプラインコンポーネント v2 は、実行環境のカスタマイズに制約があるんです。特にGPU環境でカスタムCUDAバージョンが必要な場合、Environment の構築に1〜2時間かかることがあって、開発のイテレーション速度が落ちます。

**小川:** 提案時に重要なのは「ML基盤を作って終わり」じゃなくて、モデルの再学習トリガーとモニタリングの設計まで含めることです。よくある失敗パターンは、基盤だけ作って、データドリフトの検知とか再学習パイプラインが後回しになるケース。J社で起きたのは、推薦モデルが半年間再学習されずに精度が15%劣化していて、それに気づいたのが顧客から「おすすめが的外れ」とクレームが来てからでした。

**斎藤:** プロジェクトマネジメントの観点で、この種の案件で必ずぶつかる壁があります。データサイエンティストとMLエンジニアの役割分担です。DSは「モデルの精度を上げたい」、MLEは「本番で安定稼働させたい」で、優先度が衝突するんです。最初にRACIを明確にして、「モデルの本番デプロイ判定基準」を定量的に決めておかないと、プロジェクト中盤で必ず揉めます。

**西村:** 見積もりの話ですが、この種の案件はスコープが膨らみやすいですよね。

**斎藤:** そうですね。過去の類似案件5つの実績から、初期見積りの平均1.4倍で着地してます。主な増加要因は「データの品質問題が想定以上」と「PoC から本番環境への移行工数の過小見積り」。提案時点で15〜20%のバッファを乗せて、かつ「データクレンジング工程は実データを見てから再見積り」という条件を入れるべきです。

## スクリプト 5: セキュリティインシデント対応訓練 振り返り

**会議名:** レッドチーム演習 振り返りミーティング  
**参加者:** 上田（CISO補佐）、松下（SOC リーダー）、竹内（ペネトレーションテスター）、中田（K社情シス）

---

**上田:** 先週実施したレッドチーム演習の結果を振り返ります。竹内さん、まず攻撃シナリオの概要を。

**竹内:** 初期侵入はフィッシングメールで、開発部門の3名が添付ファイルを開封しました。そこから Active Directory の横展開で、4時間でドメイン管理者権限を取得しました。最終的にファイルサーバーの機密データ（顧客DB ダンプ）の模擬持ち出しに成功しています。

**松下:** SOC 側の検知状況ですが、初期のフィッシングメール開封は EDR で検知しました。ただ、問題はその後です。横展開に使われた Pass-the-Hash 攻撃を検知したのは、ドメイン管理者権限取得の30分後でした。つまり攻撃者に4.5時間のフリータイムを与えてしまった。

**中田:** うちの環境固有の問題もあると思うんですが、何が課題でしたか？

**松下:** 一番の課題は、正規の管理者アカウントの活動と攻撃者の活動を区別する基準が曖昧だったことです。Active Directory のイベントログを見ても、管理者が日常的にリモートから各サーバーにアクセスしているので、異常な横展開と見分けがつかない。

**竹内:** ここ、アドバイスですが。「ティアモデル」と呼ばれるADの階層分離を入れると劇的に検知精度が上がります。Tier 0（ドメインコントローラー）、Tier 1（サーバー）、Tier 2（ワークステーション）で管理者アカウントを完全に分離する。これをやってる環境だと、Tier 2 のアカウントが Tier 0 にアクセスした時点でアラートが上がるので、横展開の初期段階で検知できます。

**上田:** 導入コストと期間は？

**竹内:** 正直、AD のティアモデル導入は半年〜1年の大プロジェクトです。ただ、即効性のある対策としては、ドメイン管理者アカウントのログオンを特定の端末に制限する GPO だけでも効果があります。これは1日で設定できます。

**松下:** あと一つ、演習で気づいたんですが、SOC の夜間帯（22時〜6時）の対応能力が著しく落ちます。自動化ルール（SOAR）で初動対応するようにしてるんですが、今回のような「正規アカウントの不正利用」パターンは自動遮断のルールに入ってなかった。入れると正規の管理者を誤ブロックするリスクがあるので、閾値の設計が難しいんです。

**中田:** 過去に誤ブロックでサービス影響が出たことはありますか？

**松下:** あります。去年、SOARのルールが過敏に反応して、月末バッチ処理のサービスアカウントをブロックしてしまい、経理の月次締め処理が4時間止まりました。以降、サービスアカウントはホワイトリストに入れてるんですが、今度はサービスアカウントを悪用されると検知できないというジレンマがあります。この辺のバランスは、環境ごとに「許容するリスク」を経営判断してもらうしかないんですよね。

**上田:** なるほど。リスク受容の判断基準を明文化して、経営層に承認してもらうプロセスを作りましょう。
