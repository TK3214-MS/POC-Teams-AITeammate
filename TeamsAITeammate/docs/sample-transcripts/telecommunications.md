# サンプル会議スクリプト: 通信業 (Telecommunications)

## スクリプト 1: 5G SA コアネットワーク展開計画

**会議名:** 5G SA コア展開 Phase3 計画レビュー  
**参加者:** 後藤（NW計画部長）、安田（コアNW設計）、Kim（ベンダー側SE）、三浦（運用）

---

**後藤:** 5G SA コアの Phase3 エリア展開計画について確認します。安田さん、進捗を。

**安田:** Phase3 は関西圏の UPF（User Plane Function）展開ですが、トラフィック予測の見直しが必要です。当初計画では大阪 MEC に UPF 2台構成で十分としていましたが、法人向け NW スライシングの需要が想定の3倍で来ていて、4台構成に変更すべきです。

**Kim:** UPF の追加は可能ですが、キャパシティプランニングの観点で一点。UPF 間のセッション引き継ぎ（N9インターフェース）の設計がボトルネックになります。当社の UPF 実装では、ハンドオーバー時のパケットバッファリングが最大 200ms まで対応ですが、URLLC スライスだと 10ms 以内に切り替える必要があります。前回 Phase2 の東京展開で、この制約に気づかず後から設定変更したんですが、一度本番に入れたパラメータを変更するには Change Management Board の承認が必要で、2週間かかりました。

**安田:** 最初から URLLC 対応パラメータで入れましょう。ただ、ここで注意点があって。URLLC 用パラメータにすると、eMBB（大容量通信）のスループットが 15% 落ちるトレードオフがあるんです。これ、3GPP の仕様上は同時最適化できることになってるんですが、実装レベルではバッファ配分の都合で両立しません。2022年に N社でこの問題が顕在化して、結局スライスごとに物理的に UPF を分離する設計に変更しました。

**三浦:** 運用から一つ。Phase2 で学んだ重要な教訓なんですが、UPF のソフトウェアアップデートを Rolling Update でやる場合、アクティブセッション数が10万を超えてる状態で実施すると、セッション移行がタイムアウトして一部ユーザーが切断されます。なので、トラフィックが少ない深夜3時台にやるんですが、それでも東京の UPF は常時15万セッション以上あるので、事前にトラフィック制御で片系に寄せてから更新する必要があります。このオペレーション手順、正式なランブックには書いてなくて、運用チームの口伝えです。

**後藤:** それは正式化してください。あと、MEC のロケーションですが、大阪のデータセンターは候補が3つあります。レイテンシとコストのトレードオフで選定が必要です。

**安田:** 実測ベースで、候補A（梅田）は基地局からの RTT が 3ms、候補B（堺）は 8ms、候補C（京都）は 12ms です。URLLC 要件（20ms 以下）はどれも満たしますが、将来的に V2X（車両間通信）を乗せることを考えると、候補A一択です。ただ、候補Aはラックスペースが限られてて、将来の拡張性に不安があるんですよね。2019年に東京で同じ判断ミスをして、1年後に別DCへの移設で2億円かかりました。

## スクリプト 2: 法人向け SD-WAN サービス障害対応

**会議名:** L社 SD-WAN サービス品質劣化 緊急対策  
**参加者:** 田辺（法人サービス）、井上（バックボーン）、福田（CPE運用）、Patel（ベンダーTAC）

---

**田辺:** L社さんから「午前中にVPN越しのアプリケーションが遅い」というクレームが週3回来ています。SLAの応答時間保証に抵触する可能性があるので、根本原因を特定したいです。

**井上:** バックボーン側のトラフィック分析をしました。L社のCPEが接続しているPOP（大手町）で、平日 9:00〜10:00 に帯域利用率が 92% まで上がっています。原因は、同じPOPに接続している別の大口顧客M社がバックアップジョブをこの時間帯に実行しているためです。

**福田:** CPE側のログを見ると、QoS のキューが溢れている兆候があります。具体的には、L社のビジネスクリティカルなトラフィック（Microsoft 365 + Salesforce）が、M社のバックアップトラフィックと同じキューに入ってしまっている。本来はDSCP値で分離されるはずですが。

**Patel:** I checked the CPE configuration remotely. The issue is that the DSCP remarking policy is applied on the egress interface, but M-company's backup traffic arrives at the POP already marked as AF21, which is the same class as L-company's business traffic. The CPE trusts incoming DSCP by default. We need to apply a re-classification policy at the POP ingress.

**井上:** なるほど。入口でクラシファイを入れるべきですね。ただ、ここで注意点があって。POPルーターで ACL ベースのクラシファイを入れると、処理がソフトウェアパスに落ちて、全顧客のレイテンシが微増する可能性があります。去年の名古屋POPでこれをやった時、0.5ms の遅延増が全顧客に影響して、別の法人顧客から「遅くなった」とクレームが来ました。

**田辺:** じゃあどうすれば？

**井上:** 回避策は2つ。1つはM社のバックアップ時間帯を深夜にずらしてもらう（ただし顧客交渉が必要）。もう1つは、L社のCPEでローカルブレイクアウトを設定して、Microsoft 365 と Salesforce のトラフィックは直接インターネットに出す。後者の方が根本的解決で、実はSD-WANの本来の使い方でもあります。

**福田:** ローカルブレイクアウトにする場合、L社のセキュリティポリシーとの整合性確認が必要です。L社は全トラフィックをセンター集約する方針だったはず。ただ、経験上、Microsoft 365 をセンター集約すると遅延で Teams 会議の品質が落ちるので、ほぼ全ての顧客が最終的にはローカルブレイクアウトに切り替えています。最初は抵抗されますが、CASB 経由にすればセキュリティ要件は満たせると説明すれば、大抵は了承いただけます。

## スクリプト 3: IoT プラットフォーム事業開発

**会議名:** スマートシティ向け IoT PF 事業計画レビュー  
**参加者:** 中山（新規事業部長）、大島（技術企画）、森田（パートナー営業）、Liu（海外事例）

---

**中山:** 自治体向けスマートシティ IoT プラットフォーム事業の計画を確認します。大島さん、技術面から。

**大島:** プラットフォームのアーキテクチャですが、デバイス管理・データ収集・分析・可視化の4層構成です。重要な設計判断として、通信プロトコルを何にするかがあります。自治体案件の特徴は、センサーが広域に分散配置されること、電源確保が困難な場所が多いことです。

**中山:** 候補は？

**大島:** LTE-M、LoRaWAN、Wi-SUN の3つです。結論から言うと「全部対応する」が正解です。なぜなら、過去にN市の案件で LoRaWAN 一本で提案したんですが、市役所の建物内はLoRaの電波が届かなくて、結局 LTE-M を追加する羽目になりました。逆にO市では、月額通信コストを抑えたいということでLoRaWAN前提だったのに、移動体（ゴミ収集車）のGPSトラッキングにはLTE-Mが必要だとわかり、追加発注になりました。

**森田:** ビジネスモデルの観点ですが、自治体向けはプラットフォーム利用料で月額課金するよりも、初期導入費を抑えて「データ分析サービス」として売る方が予算が通りやすいです。理由は、自治体の予算は「投資」より「サービス利用料」の方が通りやすいから。前年度予算の枠内で処理できる。P市の案件は初期費用3000万円で提案して落選しましたが、月額100万円のサービスモデルで再提案したら通りました。総額は同じなのに。

**Liu:** From the global perspective, I want to share a lesson from our Singapore deployment. We initially used a centralized cloud architecture, but the government required all citizen data to remain within national borders. We had to rebuild with edge processing capability. Japanese municipalities might have similar data residency requirements — especially after the recent Personal Information Protection law update. It's better to design for local data processing from the start.

**大島:** それは重要ですね。データ主権の問題は日本でも顕在化してきています。特に健康データや防犯カメラデータは、自治体のオンプレミスかガバメントクラウドに保持する設計にすべきです。

**中山:** 競合はどうですか？

**森田:** 一番の競合はNTTグループです。ただ、彼らの弱点は「通信インフラの売り込み」から入ること。自治体が本当に欲しいのは「課題解決」なので、うちは「住民サービス向上」のストーリーから入って、その手段として通信基盤を入れる提案にすべきです。Q市で勝てたのは、市長の「高齢者見守り」という課題にフォーカスして、技術は裏に回したからです。

## スクリプト 4: ネットワーク仮想化 (NFV) 運用自動化

**会議名:** NFV 運用自動化 成果報告 & 次期計画  
**参加者:** 岩崎（運用部長）、高田（自動化チームリーダー）、山下（NW運用）、Chang（ベンダー開発）

---

**岩崎:** NFV運用自動化のフェーズ1完了報告をお願いします。

**高田:** フェーズ1では、VNF（仮想ネットワーク機能）の Day-1 オペレーション（初期設定投入）の自動化を完了しました。Ansible + Terraform で、新規 vFirewall / vRouter の払い出しが、従来の4時間から15分に短縮されました。

**山下:** 効果は大きいんですが、正直に言うと「自動化で楽になった」のは定型作業だけで、非定型の障害対応は以前より複雑になっています。なぜかというと、NFV 環境では障害の切り分けポイントが増えるんです。従来の物理機器なら「箱を見れば分かる」だったのが、今はハイパーバイザ層、SDN コントローラー層、VNF 層のどこが原因か特定するのに時間がかかる。

**Chang:** That's a common issue. In our other deployments, we've found that the correlation between VNF health metrics and underlying infrastructure issues is not straightforward. For example, a VNF might report high CPU, but the root cause is actually a noisy neighbor on the same hypervisor host. We recommend implementing a topology-aware monitoring system that can automatically correlate alerts across layers.

**高田:** フェーズ2で計画しているのは、まさにその障害自動切り分けです。AIOps的なアプローチで、過去の障害パターンを学習させて、アラートのグルーピングと推定原因の提示を自動化したいと考えています。

**岩崎:** 懸念は？

**高田:** 一番の懸念は誤判定です。自動化が「原因はXだ」と判定して自動復旧アクションを実行した結果、実際は別の原因で、アクションが状況を悪化させるリスクがあります。去年のR社の事例では、自動復旧が VNF を再起動したら、フローテーブルが消失して全通信が一瞬途切れました。2万ユーザーに影響が出て大問題になりました。

**山下:** なので段階的に進めるべきです。最初は「人間に推奨アクションを提示するだけ」にして、半年間の精度検証を経てから自動実行に移行する。あと重要なのは、自動実行のスコープを限定すること。「VNF の再起動」はOKだけど「ネットワーク構成の変更」は人間承認必須、のようにレベル分けする。

**Chang:** One more thing — version management of the automation scripts is critical. We've seen cases where a Terraform state file got corrupted because two operators ran apply simultaneously. You need a strict state locking mechanism and a CI/CD pipeline that prevents parallel execution. Also, always tag your infrastructure versions. When a rollback is needed at 3 AM, you need to know exactly what the previous known-good state was.

**岩崎:** ステートファイルの管理は確かに重要ですね。今のところ S3 + DynamoDB ロックを使ってますが、ロック解放を忘れるケースが月に1回はある。手動でロック解放するんですが、その手順を知ってる人が3人しかいないんですよ。

## スクリプト 5: 通信料金プラン改定 技術影響アセスメント

**会議名:** 新料金プラン「つなぎ放題ライト」技術インパクト評価  
**参加者:** 白石（サービス企画）、内田（課金システム）、村田（トラフィック工学）、杉本（品質管理）

---

**白石:** 来月発表予定の新料金プラン「つなぎ放題ライト」の技術インパクトを確認します。プラン概要は、月額2,980円で20GB超過後も最大3Mbpsで使い放題です。

**村田:** トラフィック工学の観点から警鐘を鳴らしたいです。「3Mbpsで使い放題」は、ユーザー行動を劇的に変える可能性があります。現行プランでは速度制限後128kbpsなので、超過後はほぼ使わないユーザーが大半ですが、3Mbpsだと動画のSD画質が視聴できるので、超過後もずっと使い続けるユーザーが増えます。

**白石:** どのくらいの影響を見込んでますか？

**村田:** 他社の事例と弊社のシミュレーションから、超過後のトラフィックが現行の8倍に増える見込みです。特に夜間帯（19〜23時）のピークトラフィックが問題で、現行の設備計画では2026年Q3に東京圏で輻輳が発生するリスクがあります。通常だと設備増強には発注から稼働まで6ヶ月かかるので、今すぐ発注判断しないと間に合いません。

**内田:** 課金システムの観点ですが、「超過後3Mbps」の速度制御を PCRF/PCF で実現する場合、ポリシー変更のトリガーが「データ量閾値到達」です。問題は、リアルタイムでの利用量カウントの精度。現行システムは15分間隔で集計しているので、最悪の場合、閾値を超過してから速度制限適用まで15分のラグがあります。この15分で高速通信されるデータ量は、理論上最大2.7GBです。

**白石:** それは料金的に問題ないんですか？

**内田:** ユーザーにとっては得する方向なので問題ないですが、トラフィック予測に影響します。あと、もっと重要なのは、月末リセット時のシステム負荷です。月初0時に全ユーザーの速度制限が一斉解除されるので、PCRF に大量のポリシー変更リクエストが集中します。前回の料金改定時、月初0時のPCRF処理が追いつかなくて、一部ユーザーの速度が10分間制限されたままになるインシデントがありました。

**杉本:** 品質管理の観点で、3Mbps制限の実装精度も確認が必要です。現行の帯域制御はトークンバケット方式ですが、バースト許容値の設定によっては瞬間的に5Mbps以上出ることがあります。ユーザーにとってはいい話ですが、広告表現で「3Mbps」と謳って実際の体感が違うと景品表示法の問題になりえます。

**村田:** あともう一点。「3Mbps で動画が見られる」となると、ユーザーの在宅時間帯のモバイル利用が増えて、固定回線の解約が進む可能性があります。これ、他社で実際に起きて、トータルの ARPU が下がった事例があるんです。S社は2024年に同様のプランを出した結果、モバイル ARPU は微増だったんですが、光回線の解約率が1.5ポイント上がって、連結では減収でした。サービス企画としてはこのカニバリゼーションリスクも織り込むべきです。

**白石:** 確かにうちもFTTHを持ってるので、そのリスクは考えないといけませんね。マーケティングと連携して、セット割の設計を再検討します。
